# Урок 49. Аутентификация: хеширование паролей и JWT

В этом уроке мы разберём фундамент, на котором строится аутентификация в FastAPI: хеширование паролей и JWT-токены. Вы узнаете, чем аутентификация отличается от авторизации, почему пароли нельзя хранить в открытом виде и как сервер гарантирует, что токен не подделан.

---

## Часть 0. Аутентификация и авторизация

### Аналогия из жизни

Представьте ночной клуб. На входе стоит охранник:

1. Вы показываете паспорт. Охранник сверяет фото с лицом — **это аутентификация**. Охранник отвечает на вопрос: *«Кто ты?»*
2. Вы прошли внутрь. Но в конце коридора — дверь с надписью «VIP». Ваш браслет — обычный зелёный, а VIP-зона требует золотой. Вас не пускают — **это авторизация**. Система отвечает на вопрос: *«Что тебе можно?»*

### Определения

**Аутентификация** — проверка, что пользователь — тот, за кого себя выдаёт. Обычно это проверка логина и пароля.

**Авторизация** — проверка, что аутентифицированный пользователь имеет право выполнить действие или получить доступ к ресурсу. Например: обычный пользователь не может удалить чужой пост, а администратор — может.

### Зачем нужна аутентификация

Без аутентификации сервер не знает, кто делает запрос. Любой мог бы представиться кем угодно. Аутентификация привязывает запрос к конкретному пользователю.

### Зачем нужна авторизация

Даже если сервер знает, кто вы, не каждый пользователь должен иметь доступ ко всему. Авторизация разграничивает права: одни эндпоинты доступны всем, другие — только администраторам, третьи — только владельцу ресурса.

**Упражнение:**

К какой категории относится каждая ситуация — аутентификация или авторизация?

1. Пользователь вводит логин и пароль, чтобы войти в систему.
2. Сервер проверяет, что пользователь с ролью `guest` не может удалить статью.
3. Сервер проверяет, что токен в запросе действительно подписан секретным ключом.

<details>
<summary>Ответ</summary>

1. Аутентификация — проверка личности.
2. Авторизация — проверка прав.
3. Аутентификация — проверка, что токен подлинный (значит, пользователь — тот, за кого себя выдаёт).
</details>

## Часть 1. Криптография

### 1.1 Хеширование паролей

#### Что такое хеш-функция

Хеш-функция — это функция, которая принимает произвольную строку и возвращает строку фиксированной длины. Важно: хеш-функция **односторонняя** — из хеша нельзя восстановить исходную строку.

**Аналогия:** хеш-функция — как мясорубка. Закинули кусок мяса (пароль) — получили фарш (хеш). Из фарша собрать обратно кусок мяса невозможно. Но если закинуть тот же кусок мяса снова — получится точно такой же фарш. Поэтому хеш можно использовать для проверки: «тот же пароль или нет» — не зная самого пароля.

Пример хеша (встроенная функция `hash` в Python для демонстрации принципа):

```python
print(hash("mypassword"))
# 1234567890123456789 (число, разное на каждом запуске Python)
```

`hash()` в Python — нестабильная функция (результат меняется между запусками). Для паролей используют специальные криптографические хеш-функции, которые дают одинаковый результат на любом компьютере.

#### Почему нельзя хранить пароли в открытом виде

Представьте, что вы храните пароли в базе данных как есть:

```
users table:
  username | password
  alice    | qwerty123
  bob      | ilovedogs
```

Если база утечёт (а утечки случаются) — все пароли скомпрометированы. Пользователи часто используют один и тот же пароль на нескольких сервисах. Утечка пароля от вашего сайта = доступ к почте, соцсетям, банку.

Если же хранить хеши:

```
users table:
  username | password_hash
  alice    | $argon2id$v=19$m=...
  bob      | $argon2id$v=19$m=...
```

То при утечке базы злоумышленник получит набор хешей. Восстановить из них пароли невозможно (мясорубка не работает в обратную сторону). Сервер при этом может проверить пароль при входе: захешировать введённый пароль и сравнить с хешем из базы.

#### Как делать в Python — библиотека `pwdlib`

**Документация:** [pwdlib on PyPI](https://pypi.org/project/pwdlib/)

Установка:

```bash
pip install pwdlib[argon2]
```

`pwdlib` предоставляет два метода:

- `hash(password)` — получить хеш для хранения
- `verify(plain, hashed)` — проверить, что введённый пароль соответствует хешу

Пример:

```python
from pwdlib import PasswordHash

password_hasher = PasswordHash.recommended()

hashed = password_hasher.hash("mypassword")
print(hashed)
# $argon2id$v=19$m=65536,t=3,p=4$...

is_correct = password_hasher.verify("mypassword", hashed)
print(is_correct)
# True

is_wrong = password_hasher.verify("wrongpassword", hashed)
print(is_wrong)
# False
```

Обратите внимание: `verify` не выбрасывает ошибку при неверном пароле — он возвращает `False`. Ошибка выбрасывается только при проблемах с самим хешем (повреждён, неверный формат).

Интересный момент: если захешировать один и тот же пароль дважды, хеши будут **разными**:

```python
hash1 = password_hasher.hash("mypassword")
hash2 = password_hasher.hash("mypassword")
print(hash1 == hash2)
# False
```

Это не баг — это **соль** (salt). К каждому паролю при хешировании добавляется случайная строка, которая хранится прямо внутри хеша. Поэтому хеши разные, но `verify` всё равно работает:

```python
print(password_hasher.verify("mypassword", hash1))  # True
print(password_hasher.verify("mypassword", hash2))  # True
```

Соль защищает от атак по радужным таблицам — заранее вычисленным хешам популярных паролей. С солью каждый хеш уникален, даже для одинаковых паролей.

**Упражнение:**

Что выведет этот код?

```python
hashed = password_hasher.hash("secret")
print(password_hasher.verify("secret", hashed))
print(password_hasher.verify("SECRET", hashed))
```

<details>
<summary>Ответ</summary>

```
True
False
```

Хеширование чувствительно к регистру. `"secret"` и `"SECRET"` — разные пароли.
</details>

### 1.2 JWT (JSON Web Token)

#### Что это

JWT — это строка, в которой хранятся данные и подпись. Сервер создаёт токен, кладёт в него нужные данные (например, имя пользователя) и подписывает своим секретным ключом. Клиент получает токен и отправляет его с каждым запросом. Сервер проверяет подпись — если она верна, данные в токене можно доверять.

**Аналогия из жизни:** JWT — как печать в паспорте. Печать ставится секретным клише (секретный ключ). Видеть печать может кто угодно, но подделать без клише невозможно. Сервер — единственный, у кого есть клише.

#### Ключевая идея

Сервер подписывает токен секретным ключом. Проверить токен может только тот, кто знает ключ. Без секретного ключа подделать подпись невозможно.

#### Алгоритм HS256

В этом курсе мы будем использовать алгоритм `HS256` — это надёжный симметричный алгоритм. Под капотом он использует один и тот же секретный ключ для подписи и для проверки. Детали реализации не так важны — главное понимать: без ключа подделать токен нельзя.

#### Что внутри токена

В payload (данные токена) мы кладём поля:

| Поле | Название | Что значит |
|---|---|---|
| `sub` | Subject | Идентификатор пользователя. Мы кладём туда `username` |
| `iat` | Issued At | Когда токен выдан (unix-timestamp) |
| `exp` | Expiration | Когда токен истекает (unix-timestamp) |

`pyjwt` автоматически проверяет `exp` при декодировании. Если токен просрочен — `decode` выбросит ошибку, вам не нужно проверять это вручную.

#### Как делать в Python — библиотека `pyjwt`

**Документация:** [PyJWT on PyPI](https://pypi.org/project/PyJWT/)

Установка:

```bash
pip install pyjwt
```

Создание токена — `jwt.encode(payload, secret, algorithm)`:

```python
import jwt
from datetime import datetime, timedelta

SECRET_KEY = "my-super-secret-key"

payload = {
    "sub": "alice",
    "iat": datetime.now().timestamp(),
    "exp": (datetime.now() + timedelta(seconds=3600)).timestamp(),
}

token = jwt.encode(payload, SECRET_KEY, algorithm="HS256")
print(token)
# eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhbGljZSIsIml...
```

Проверка и чтение токена — `jwt.decode(token, secret, algorithms)`:

```python
decoded = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
print(decoded)
# {'sub': 'alice', 'iat': 1700000000.0, 'exp': 1700003600.0}
```

Обратите внимание: `algorithms` передаётся **списком**, даже если алгоритм один. Это защита от уязвимостей, когда атакующий указывает другой алгоритм в header.

#### Что происходит при ошибке

Если токен подделан (другой секретный ключ) — `jwt.decode` выбрасывает `PyJWTError`:

```python
try:
    jwt.decode(token, "wrong-secret-key", algorithms=["HS256"])
except jwt.PyJWTError as e:
    print("Токен недействителен:", e)
    # Токен недействителен: Signature verification failed
```

Если токен просрочен — `jwt.ExpiredSignatureError` (наследник `PyJWTError`):

```python
expired_payload = {
    "sub": "alice",
    "iat": datetime.now().timestamp(),
    "exp": (datetime.now() - timedelta(seconds=1)).timestamp(),  # уже истёк
}
expired_token = jwt.encode(expired_payload, SECRET_KEY, algorithm="HS256")

try:
    jwt.decode(expired_token, SECRET_KEY, algorithms=["HS256"])
except jwt.ExpiredSignatureError as e:
    print("Токен просрочен:", e)
    # Токен просрочен: Signature has expired
```

## Часть 2. Паттерны проектирования

### 2.1 Singleton через модуль

#### Что такое singleton

Singleton — это паттерн проектирования, который гарантирует, что у класса существует **только один экземпляр** на всё приложение.

**Аналогия:** пульт от телевизора в квартире. Кто бы ни попросил пульт — всем дают один и тот же. Не существует двух пультов от одного телевизора. Если кто-то переключил канал — это видят все, потому что пульт один.

#### Зачем нужен singleton в нашем случае

В проекте есть конфигурация: секретный ключ, алгоритм, срок жизни токена. Эти данные читаются из `.env` один раз при старте приложения. Нет смысла создавать конфиг заново в каждом модуле — это лишняя работа и потенциальные расхождения. Нужен один объект, доступный всем.

#### Простейший singleton в Python — код на уровне модуля

В Python модуль выполняется **один раз** при первом `import`. Результат кешируется в `sys.modules`. Все последующие импорты получают уже загруженный модуль. Это значит, что любой объект, созданный на уровне модуля (не внутри функции, не внутри класса), автоматически становится singleton.

Можно реализовать singleton через класс с `__new__` или метакласс, но для нашего случая это оверинжиниринг. Код на уровне модуля — самый простой и идиоматичный способ в Python.

#### Пример: конфигурация аутентификации

Создадим файл `config.py`:

```python
import os
from pydantic import BaseModel
from dotenv import load_dotenv

load_dotenv()


class AuthConfig(BaseModel):
    SECRET_KEY: str
    ALGORITHM: str = "HS256"
    EXP_DATE: int = 3600


auth_config = AuthConfig(
    SECRET_KEY=os.getenv("SECRET_KEY"),
    ALGORITHM=os.getenv("ALGORITHM", "HS256"),
    EXP_DATE=int(os.getenv("EXP_DATE", "3600")),
)
```

Файл `.env`:

```env
SECRET_KEY=my-super-secret-key
ALGORITHM=HS256
EXP_DATE=3600
```

Теперь в любом другом модуле можно импортировать `auth_config` и получить тот же самый объект:

```python
from config import auth_config

print(auth_config)
# SECRET_KEY='my-super-secret-key' ALGORITHM='HS256' EXP_DATE=3600

print(auth_config.SECRET_KEY)
# my-super-secret-key
```

Что здесь происходит:

1. При первом `from config import auth_config` Python выполняет `config.py` целиком: `load_dotenv()` читает `.env`, создаётся `AuthConfig`, переменной `auth_config` присваивается экземпляр.
2. При следующем импорте `config` из другого модуля Python находит модуль в кеше `sys.modules` и не выполняет его повторно. Все получают тот же объект `auth_config`.

Pydantic здесь даёт бонус: если `SECRET_KEY` не будет найден в `.env`, `os.getenv` вернёт `None`, и Pydantic выбросит `ValidationError` ещё при импорте модуля — ошибка всплывёт сразу, а не в рантайме.

**Упражнение:**

Если модуль `config` импортируют из двух разных файлов, создастся два экземпляра `auth_config` или один? Почему?

<details>
<summary>Ответ</summary>

Один. Python выполняет модуль один раз при первом импорте и кеширует результат в `sys.modules`. При втором импорте модуль не выполняется заново — возвращается уже загруженный модуль с тем же объектом `auth_config`.
</details>

### 2.2 Абстракции

#### Что такое абстракция

Абстракция — это когда мы описываем **что** должен делать объект, но не **как** он это делает. Код, который использует объект, работает с интерфейсом и не знает о деталях реализации.

**Аналогия:** розетка. Форма стандартизирована — это интерфейс. Что за стеной — медный провод, алюминиевый, подстанция на другом конце города — неважно. Любой прибор работает с любой розеткой, потому что интерфейс одинаковый.

#### Зачем это в нашем проекте

В проекте нужно хранить пользователей. Сейчас можно хранить их в списке в памяти. Потом — в файле. Ещё потом — в базе данных. Если код, который работает с хранилищем, завязан на конкретную реализацию (список), при переходе на базу данных придётся переписывать всё. Если код работает с абстракцией — достаточно создать новый класс с той же реализацией интерфейса.

#### Абстрактный класс в Python

Python предоставляет модуль `abc` (abstract base classes) для создания абстрактных классов. Абстрактный класс нельзя создать напрямую — можно только унаследоваться от него и реализовать все абстрактные методы.

Создадим абстрактный класс `UserStorage` — он описывает, что умеет хранилище пользователей, но не как:

```python
from abc import ABC, abstractmethod


class UserStorage(ABC):
    @abstractmethod
    def get_by_username(self, username: str) -> dict | None:
        ...

    @abstractmethod
    def exists(self, username: str) -> bool:
        ...

    @abstractmethod
    def create(
        self,
        username: str,
        password_hashed: str,
        first_name: str,
        second_name: str,
    ) -> dict:
        ...
```

Теперь создадим конкретную реализацию — `UserDict`, который хранит пользователей в `list[dict]`:

```python
class UserDict(UserStorage):
    def __init__(self) -> None:
        self._users: list[dict] = []

    def get_by_username(self, username: str) -> dict | None:
        for user in self._users:
            if user['username'] == username:
                return user
        return None

    def exists(self, username: str) -> bool:
        return any(user['username'] == username for user in self._users)

    def create(
        self,
        username: str,
        password_hashed: str,
        first_name: str,
        second_name: str,
    ) -> dict:
        user = {
            'username': username,
            'password_hashed': password_hashed,
            'first_name': first_name,
            'second_name': second_name,
        }
        self._users.append(user)
        return user
```

Теперь напишем функцию, которая работает с хранилищем. Она принимает `UserStorage` — абстрактный тип:

```python
def print_user_info(storage: UserStorage, username: str) -> None:
    """Работает с абстракцией — не знает, откуда берутся данные."""
    if not storage.exists(username):
        print(f"Пользователь {username} не найден")
        return
    user = storage.get_by_username(username)
    print(f"{user['first_name']} {user['second_name']}")


storage = UserDict()
storage.create("alice", "hash123", "Alice", "Smith")
print_user_info(storage, "alice")
# Alice Smith
```

`print_user_info` принимает `UserStorage` — абстрактный тип. Функция не знает и не должна знать, откуда приходят данные: из списка в памяти, из файла, из базы данных. Она просто вызывает `exists` и `get_by_username` — они есть в любом наследнике `UserStorage`.

Позже можно создать `UserJson(UserStorage)` с хранением в файле или `UserDatabase(UserStorage)` с обращением к базе данных — функция `print_user_info` не изменится.

**Упражнение:**

Если создать класс `UserJson(UserStorage)` с хранением в файле, нужно ли переписывать функцию `print_user_info`? Почему?

<details>
<summary>Ответ</summary>

Нет. `print_user_info` принимает `UserStorage` — абстрактный тип. `UserJson` наследуется от `UserStorage`, поэтому его можно передать в функцию. Функция вызывает `exists` и `get_by_username` — они есть в любом наследнике. Это и есть сила абстракции: код работает с интерфейсом, а не с реализацией.
</details>

## Итоги

- **Аутентификация** отвечает на вопрос «кто ты?», **авторизация** — «что тебе можно?». Сначала аутентификация, потом авторизация.
- Пароли нельзя хранить в открытом виде. Хеш-функция необратима: из хеша нельзя восстановить пароль, но можно проверить совпадение.
- `pwdlib` предоставляет `hash()` для получения хеша и `verify()` для проверки пароля. Одинаковые пароли дают разные хеши благодаря соли.
- JWT — строка с данными и подписью. Без секретного ключа подделать подпись невозможно. Мы используем `HS256` — надёжный симметричный алгоритм.
- `sub` — идентификатор пользователя, `iat` — время выдачи, `exp` — срок истечения. `pyjwt` автоматически проверяет `exp`.
- `jwt.encode()` создаёт токен, `jwt.decode()` проверяет и читает. Ошибки — `PyJWTError` (и `ExpiredSignatureError` как частный случай).
- Singleton через код на уровне модуля — простейший способ гарантировать один экземпляр объекта. Модуль в Python выполняется один раз, результат кешируется.
- Абстракция — описание **что** делает объект, а не **как**. Абстрактный класс задаёт интерфейс, наследники — реализацию. Код, работающий с абстракцией, не меняется при смене реализации.

### Задание 5. Модуль `utils/auth` (~20 мин)

Создайте модуль `utils/auth.py`, который объединяет хеширование паролей и JWT в готовые функции. Структура модуля:

#### `auth_config`

Singleton-объект — экземпляр Pydantic-модели `AuthConfig`, наполненный данными из `.env`. Поля:

| Поле | Источник | Описание |
|---|---|---|
| `SECRET_KEY` | `SECRET_KEY` из `.env` | Секретный ключ для подписи JWT |
| `ALGORITHM` | `ALGORITHM` из `.env` | Симметричный алгоритм (`HS256`) |
| `EXP_DATE` | `EXP_DATE` из `.env` | Количество секунд до истечения токена |

Реализуется как код на уровне модуля (см. часть 2.1). Модель `AuthConfig` — наследник `BaseModel`.

#### `get_token(data: dict) -> str`

- Добавляет в `data` поле `iat` — текущее время
- Добавляет в `data` поле `exp` — текущее время + `EXP_DATE` из `auth_config`
- Подписывает токен при помощи `SECRET_KEY` и `ALGORITHM` из `auth_config`
- Возвращает строку токена

#### `decode_token(token: str) -> dict`

- Возвращает данные из токена

#### `get_hashed_password(password: str) -> str`

- Возвращает хеш пароля через `pwdlib`

#### `is_hashed_equal(plain_password: str, hashed_password: str) -> bool`

- Проверяет, что открытый пароль соответствует хешу, через `pwdlib`
- Возвращает `True` или `False`

#### Проверка

Создайте файл `.env`:

```env
SECRET_KEY=my-super-secret-key
ALGORITHM=HS256
EXP_DATE=3600
```

Убедитесь, что:

1. `get_hashed_password("test")` возвращает строку-хеш
2. `is_hashed_equal("test", ...)` с этим хешем возвращает `True`
3. `get_token({"sub": "alice"})` возвращает строку токена
4. Декодирование токена вручную через `jwt.decode` возвращает payload с `sub`, `iat`, `exp`
5. Попытка декодировать токен с другим секретным ключом выбрасывает `PyJWTError`

### Задание 6. Класс `UserJson` (~15 мин)

В уроке мы создали абстрактный класс `UserStorage` и реализацию `UserDict` с хранением в `list[dict]`. Реализуйте класс `UserJson(UserStorage)` — хранилище пользователей в JSON-файле.

1. `__init__(self, filepath: str)` — путь к JSON-файлу. Если файл не существует — создавать пустой список.
2. `get_by_username` — читать файл, искать пользователя по `username`
3. `exists` — читать файл, проверять наличие
4. `create` — читать файл, дописать пользователя, записать обратно

**Проверка:**

```python
storage: UserStorage = UserJson("users.json")
storage.create("bob", "hash456", "Bob", "Jones")
print(storage.exists("bob"))  # True
print_user_info(storage, "bob")  # Bob Jones

# Тот же код работает и с UserDict — ничего не меняем
storage2: UserStorage = UserDict()
storage2.create("alice", "hash123", "Alice", "Smith")
print_user_info(storage2, "alice")  # Alice Smith
```
